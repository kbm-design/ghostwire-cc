# Ghostwire (Notch Command Center) — agent build guide

Native macOS notch app. A **context-mobility companion**: observe + gate AI coding agents, hold context, surface ambiently — without leaving your flow. Forked from Buddi (boring.notch window/animation + Claude Island hook integration).

Full project context lives in the Obsidian vault: `keelo/projects/notch-command-center/` — **start with `CLAUDE.md` (living status) + `Roadmap research — synthesis & priorities.md`**. Roadmap is tracked in Linear team **GW** across 6 projects. This file is the build-time guide for coding agents working in this repo.

## Build & run
- **Build/run with the scheme, NOT a bare target:** `xcodebuild -scheme Ghostwire ...` (a bare `-target` fails with `no such module 'Defaults'` — the SPM products link via the scheme). Project: `Ghostwire.xcodeproj`.
- Non-sandboxed (needs Unix-socket + file access) → not Mac App Store; distributed via direct download / Homebrew.

## Architecture — where things live (under `Ghostwire/`)
- **Agent integration** — `Services/Hooks/` (`HookInstaller`, `CodexHookInstaller`, `HookSocketServer`), `Services/Session/` (`ClaudeSessionMonitor`, `AgentFileWatcher`, `JSONLInterruptWatcher`, `ConversationParser`, `ChatHistoryManager`), `Services/State/SessionStore.swift`, `Services/Tmux/` (incl. `ToolApprovalHandler`), `Services/Window/` (finder/focuser/Yabai), `Services/Shared/` (`UsageService`, `ProcessTreeBuilder`, `TerminalAppRegistry`).
- **Notch shell (inherited base)** — `components/Notch/` (`GhostwireSkyLightWindow`, `NotchShape`), `private/CGSSpace.swift`, `managers/NotchSpaceManager.swift`. Borderless `NSPanel` in a `CGSSpace` at high window level; the notch is a *drawn* shape. Don't redesign — extend.
- **Capability surfaces (inherited)** — `managers/` (Music/Calendar/Battery/Brightness/Volume/Webcam), `MediaControllers/` (per-app + `NowPlayingController`), and **`components/Shelf/`** — a hold-store of `ShelfItemKind = .file(bookmark)/.text/.link` with security-scoped bookmarks + persistence. The Shelf **is** the context hold-store the roadmap builds on.
- **MCP (both directions, one swift-sdk `MCP` dep)** — `Services/MCP/`. **Client/consume (GW-219):** `MCPClientService` (allowlist choke point) + `MCPConnection` + `StdioServerProcess` connect *out* to external servers. **Server/serve (GW-173):** `MCPServeRuntime` + `ShelfContextProvider` + `MCPServeRegistration` expose the Shelf read-only so agents *pull* held context. The server runs as the **`Ghostwire mcp-serve` subcommand of the same binary** (entry interception in `GhostwireApp.swift`) — same code signature so `.withSecurityScope` Shelf bookmarks resolve; no GUI init. Serve read path is **nonisolated** (no `@MainActor`/`ShelfStateViewModel` — a headless stdio process has no run loop to drain main-actor work; reads `ShelfPersistenceService.storeURL` directly, read-only). Tools: `get_held_items` / `search_saves` / `get_item`. Consent gate `Defaults[.mcpServeEnabled]` (default off); UI in the **Agents tab → "Shelf access"** (the app never writes agent config — copy-paste only). **Gateway/re-expose (GW-253):** `MCPGatewayCore` + `GatewayHTTPService`/`GatewayServer`/`GatewayHTTPListener` re-expose held downstream servers as **one localhost HTTP connector** external chat apps add once (namespaced `‹app›_‹tool›`); persistent Keychain bearer token; GW-184 bounds the exposed set (working-set + `search_tools`/`call_tool` fallback). **Hosted-server auth (GW-291/292, shipped v0.1.8):** an `.http` server authenticates via a per-server `MCPHTTPAuth` — static API-key/Bearer header **or** a pre-registered OAuth client (client_id + optional secret + pinned loopback); `nil` = SDK dynamic client registration; secrets in Keychain. Don't re-add the swift-sdk dep or fork a parallel protocol layer.
- **UI** — `Ghostwire/UI/` (`ChatView` / `InstanceRow` / approval bar; `Views/FeedCardView`+`FeedSurfaceView` for the Feed tab, GW-259; `Settings/MCPSettingsView`+`MCPServerDetailView`), `components/Tabs/`. Notch tabs: **Agents · Shelf · Feed** (+ module tabs); a `GhostwireSurface` `.notch`/`.window` flag renders the same views in the detached window (GW-223).
- **Interaction states (epic GW-269, all four shipped).** `ChatView` dispatches a pending gate by tool name: `AskUserQuestion` → `ChatChoiceBar` (State B), `ExitPlanMode` → `ChatPlanReviewBar` (State C), anything else → `ChatApprovalBar` (State A); no gate + `waitingForInput` → the composer (State D). B and C each parse `activePermission.toolInput` into a typed `Codable` payload (`AskUserQuestionPayload` / `ExitPlanModePayload`) and **return nil rather than render a partial payload** — the caller falls back to the verbatim approval bar, because answering something you were never fully shown is worse than being sent to the terminal. Both bars share one shape: delivery state machine, one-shot lock, GW-163 sent/failed glyph, Terminal escape hatch. Spec: the Interaction Model doc §3–§5; verified payloads in [`docs/interaction-model-payloads.md`](docs/interaction-model-payloads.md).
- **`GhostwireMarkdownText` is inline-only** (`.inlineOnlyPreservingWhitespace`) — right for a chat turn, wrong for anything with headings, lists or fenced code, which render as literal characters. That is why `PlanMarkdownView` exists (GW-322). Don't "fix" the shared renderer to solve a block-content problem.

## Hook / approval contract
- Agents → lifecycle hooks → **Unix socket `/tmp/com.ghostwire.notch.sock`** (`HookSocketServer`) → `SessionStore` → notch UI. Approve/Deny writes the verdict back over the held socket (`hookSpecificOutput.decision.behavior` = allow/deny).
- **`ExitPlanMode` is the exception: a bare `{"behavior":"allow"}` is SILENTLY DISCARDED** (GW-322, measured on `claude 2.1.222`). No `PostToolUse` fires, the terminal's own plan menu stays up, and nothing logs an error — the notch says "Accepted" over a terminal that is still waiting. It needs `decision.updatedInput` (echo `tool_input` back). Verified that a bare allow still works for `Write`, so `ghostwire-hook.py` scopes the `updatedInput` to `tool_name == "ExitPlanMode"` rather than round-tripping every payload. **If another tool ever starts ignoring an allow, this is the first thing to try.** Accepting this way lands `permission_mode: default` ("manually approve edits"), never auto mode — keep it that way, the notch must not grant broader permissions than the terminal would for the same click.
- **`PermissionRequest` carries no `tool_use_id`** → correlate via a cache keyed off the preceding `PreToolUse` (FIFO by sorted input). Headless `claude -p` never fires interactive `PermissionRequest`.
- **Gate States B/C at `PermissionRequest`, never `PreToolUse`** (GW-318/GW-322). Both events fire ~1s apart carrying an *identical* `tool_input`, so either could render — the choice is entirely about the race. Holding `PreToolUse` suppresses the terminal's own menu (measured: it never rendered during a 25s hold), which buys race-freedom by making the notch a single point of failure for the user's agent. Holding `PermissionRequest` leaves the terminal usable — its menu renders ~6s in — so the race is real and spec §5 invalidation carries it.
- **Deny-with-message is how a hook "answers".** No hook field supplies a real tool result, so a Choice answer (State B) and plan-revision feedback (State C) both ride `decision.message`, which the model reads as the answer. It must be **one-shot per gate** — a replayed message is model-visible (GW-318 caught the model calling out "replaying stale feedback"). Unlike State D this needs no addressable pane, so it works outside tmux/cmux.
- Codex hooks mirror Claude's schema at `~/.codex/hooks.json` (no `SessionEnd`/`Notification`); needs a one-time `/hooks` trust per hook change. Codex transcripts/usage live at `~/.codex/sessions/**/rollout-*.jsonl` (different schema/path from Claude's `~/.claude/projects/**/*.jsonl`).
- **Hook script** is `Ghostwire/Ghostwire/Resources/ghostwire-hook.py` (buddi→Ghostwire rename complete, GW-152). GW-175 generalized the installer (`GenericHookInstaller` + `HookInstallSpec`) with a `GHOSTWIRE_AGENT` normalize/denormalize adapter so one hook serves Claude/Cursor/Copilot/Factory/etc.; a few legacy `buddi`/`BUDDI_` strings persist as transitional bridges in the installers — match what a given file already uses.
- **A dropped gate event FAILS OPEN — the tool runs unseen.** If the app can't decode a `PermissionRequest`, the socket closes with no verdict, the script's `send_event` returns `None`, and the hook exits 0 to let the agent proceed (deliberate: app down must not wedge an agent). So decoding is deliberately lenient (GW-341): **only `session_id`/`cwd`/`event`/`status` may throw** in `HookEvent.init(from:)` — every optional field is best-effort and degrades to nil. Never tighten an optional field into a hard requirement; a shape drift in one field would silently cost approvals. Note `tool_input` is **not always an object** — Cursor's `beforeMCPExecution` sends it JSON-encoded as a *string*.
- **`GHOSTWIRE_AGENT` names the config file the hook lives in, NOT the agent that is running.** `cursor-agent` also executes the hooks in `~/.claude/settings.json`, so one Cursor turn fires both configs and the Claude copy reports the same events as `source=claude` (GW-341). Identity therefore comes from the payload: **Cursor stamps `cursor_version` on every event** (`conversation_id` is *not* a discriminator — Cursor sends `session_id` too). `_detect_agent()` fingerprints on that and stays silent when the detected agent has its own hook installed, because reporting twice means **two approval prompts for one tool call**. Add a new agent's fingerprint to `_AGENT_FINGERPRINTS` + `_AGENT_CONFIG_DIRS`, don't trust the env var alone.
- **Debugging the stream:** `/usr/bin/log stream --level debug --predicate 'subsystem == "com.ghostwire.notch" AND (category == "Hooks" OR category == "Session")'` (absolute path — `log` is shadowed by a zsh builtin). `Received:` carries `source=`, and `SessionStore` logs `New session … agent=…` / `agent corrected: X -> Y`. To find *who* sent a mis-sourced event the app log can't help — temporarily patch the **installed** `~/<agent>/hooks/ghostwire-hook.py` to walk `ps -o ppid=,command=` up the tree and dump `sorted(data.keys())`, then restore (the app re-copies from the bundle on launch anyway).

## Build principles (read before designing features)
- **Terminal support is TIERED — tmux/cmux are NEVER hard dependencies.** Baseline = plain/normal terminal (focus frontmost terminal, keystroke/paste injection). tmux adds pane targeting. cmux adds rich surface addressing (`CMUX_SURFACE_ID`, `surface.send_text`). **Build degraded-but-functional first;** cmux/tmux are progressive enhancement (applies to pane-targeting GW-162 + send-to-agent inject GW-164).
- **Local-first / privacy.** Observation, the Shelf store, and the MCP transport are local. Data crosses the wire only on an actual tool execution (the invoked content, to the agent the user chose; a local agent → nothing leaves). **Never narrate the user's activity to a cloud agent** to auto-pick tools — tool exposure is curated pinned plugins + a search fallback, not a context-aware router.
- **Moat ≠ the approval UI.** The approval/observe core is commoditized (xisland/notchi/agentnotch ship it). The wedge is context-mobility + ambient context-ranking + the agent/context layer. Don't over-invest in approval polish as if it were the differentiator.
- **License hygiene (reference repos in `../reference-repos/`):** **notchi & cmux are GPL** → read as a spec, reimplement clean-room, **do not copy their source**; interop with cmux only via its socket/CLI/env-var contracts. **PikoChan / CodeIsland / agentnotch are MIT** → borrow directly (agentnotch's `CGSSpace.swift` is MPL — keep its header). NCC is itself a GPL fork (via Buddi) — keep LICENSE/attribution intact.

## Conventions
- Match surrounding Swift style. The notch substrate (windowing/animation/tabs) is stable — changes for the agent surface live in `Ghostwire/Services` + `Ghostwire/UI` + the live-activity/tab insertion points. Build must stay clean; smoke-test agent flows in a real Claude Code + Codex session.
